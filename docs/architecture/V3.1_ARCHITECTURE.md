## 1. 十八个概念问题（逐一定义）

### 1.1 什么是 Artifact？

**系统已经产生的、可引用、可追踪、可验证、可版本化的研究对象。**

- 15 种类型：`problem, question, assumption, model, dataset, code, experiment, result, figure, table, claim, decision, narrative, paper_section, deliverable`
- Artifact ≠ 文件。文件是 Artifact 的 `payload`（载荷），一个 Artifact 可以引用多个文件；Artifact 的身份是 **Stable ID**，不是路径。
- V2 的 `work/question_spec.json` 等产物在 V3 中是 `Q001` 等 Artifact 的 payload。`paper/main.pdf` 是 `deliverable` 类型 Artifact——它与 `model M001` 在 Registry 中地位平等，**没有任何 Artifact 是"终点"，只有 lifecycle 状态不同**。
- 每个 Artifact 遵守统一 Contract（§1.11）。

### 1.2 什么是 State？

**系统现在处于什么状态——是派生视图，不是内容仓库。**

V3 State 是多维的，持久化为 `projects/<p>/state/status.json`：

```json
{
  "schema_version": 3,
  "problem":  {"status": "parsed"},
  "questions": {
    "Q001": {"status": "validated", "models": ["M001"], "claims": ["C001"]},
    "Q002": {"status": "experimenting", "models": ["M002"], "experiments": ["E003"]}
  },
  "evidence": {"graph_version": 7, "claims_supported": 5, "claims_total": 8},
  "workflow": {"current_nodes": ["experiment_Q002"], "blocked": [], "retries": {}},
  "run": {"phase": "experiment", "updated_at": "..."}
}
```

- State **不存储研究内容**——内容在 Artifact payload；State 只存状态与聚合视图。
- State 由 runtime 推导/维护，Workflow 引擎读写它来决定下一步。
- 29-step 编号退役为 legacy 兼容层（见 §1.18）。

### 1.3 什么是 Evidence？

**Artifact 之间的 typed relation 集合，回答"哪些证据支撑哪些主张"。**

- Evidence Graph 是有向带类型图：节点 = Stable ID，边 = relation type。
- **14 种 relation**（全部单向、语义固定）：

| relation | from → to | 语义 |
|---|---|---|
| `motivates` | problem → question | 问题分解出子问题 |
| `solved_by` | question → model | 子问题由模型求解 |
| `assumes` | model → assumption | 模型依赖假设 |
| `implemented_by` | model → code | 模型由代码实现 |
| `validated_by` | model → experiment | 模型由实验验证 |
| `tests` | experiment → model | 实验检验模型（反向视角） |
| `uses` | experiment → dataset / code | 实验使用数据/代码 |
| `produces` | experiment → result | 实验产出结果 |
| `visualized_by` | result → figure / table | 结果由图表呈现 |
| `supports` | result → claim | 结果支撑主张 |
| `appears_in` | claim → paper_section | 主张出现在章节 |
| `selects` | decision → model | 决策选定模型 |
| `based_on` | decision → any | 决策基于证据 |
| `derived_from` | any → any | 通用派生（payload 级追溯） |

- 覆盖率（supported_claims / total_claims）是 Evidence Gate 的核心指标。
- V2 的 `all_results.json` 是本图的**退化扁平投影**（legacy 适配器负责双向转换，§1.18）。

### 1.4 什么是 Workflow？

**下一步做什么的控制逻辑——操作 State + Registry + Graph，不直接依赖"某文件是否存在"。**

- Workflow 是 DAG：节点 = 认知步骤（problem_analysis / model_critique / experiment_Qi / evidence_gate / paper_projection...），边 = 依赖 + 条件（on_pass/on_fail）+ 反馈环。
- 三层组合（Composition）：`workflows/base.yaml`（骨架）+ `workflows/competition/<comp>.yaml`（赛事 profile 覆盖）+ 项目 State（Per-Qi 展开、跳过已完成）→ **可执行 workflow**。
- 引擎能力：ready-node 计算、并行组、条件边、反馈环（critic fail → 回退上游节点）、重试上限、blocked 节点、partial rerun（只重跑被 invalidation 标脏的 Qi 子图）。
- **节点 ≠ Agent**。节点引用 capability（skill 组合），由 runtime executor 执行。

### 1.5 什么是 Knowledge？

**帮助 Agent 做更好选择的决策知识，不是让 Agent 读更多文档的文档库。**

三层结构（`core/knowledge/`）：

1. **Method Cards**（`methods/cards/*.yaml`）：机器可读方法卡片——good_for / requires / risks / validation / often_combined_with / anti_patterns。检索输出"候选方法 + 适用条件 + 风险 + 验证方式 + 历史失败案例"。
2. **Failure Memory**（`failures/*.yaml`）：failure_id / problem_context / method / failure_mode / symptom / root_cause / detection / fix / avoidance。
3. **Innovation Patterns**（`patterns/*.yaml`）：pattern_id / problem_type / baseline_method / innovation / required_evidence / risks / examples。

现有 276 个 Markdown 文档**不删除、不强行结构化**——保留为 human-readable 参考资料，结构化卡片按需从其蒸馏（P2 先做 12-16 张高频卡）。检索 API 是 `KnowledgeRetriever`，输入问题特征向量，输出排序后的决策建议包。

### 1.6 什么是 Decision？

**参与未来决策的连续决策记忆，不是历史日志。**

V3 Decision Log（`projects/<p>/state/decisions.json`，schema 升级自 V2 `decision_log.schema.json`）：

- 必填：`decision_id / question / chosen / alternatives / criteria / evidence_ids / reasoning / confidence / reversible / created_by`
- 决策可被 **invalidated**（`invalidated_by` 指向新决策或 invalidation 事件），失效决策在检索时降权并附带"为何被推翻"。
- 检索 API：按 question 类型 / method / 当前问题特征查询历史决策，供 method-selection 与 critic 消费。

### 1.7 Agent 和 Skill 的关系？

```
Skill   = 单一可执行能力单元（prompt + procedure + self-check + 工具绑定）
Agent   = Runtime Executor：加载 skill 组合 + 上下文，执行 workflow 节点
```

- Skill 是能力的**声明**，Agent 是能力的**运行时实例化**。
- "Skill + Prompt + Validator"形态的单元（如 V2 的 5 个 scorer）**不配为 Agent**——降级为 validator 或 critic skill。

### 1.8 Role 和 Agent 的关系？

```
Role    = Capability Composition（能力组合的命名模板）
Agent   = 承载 Role 的运行时执行器
```

五个 Role（`core/roles/*.yaml`）：`analyst / modeler / experimenter / critic / writer`。每个 Role 声明其 capability 列表（对应 skills），例如：

```yaml
role: modeler
capabilities: [problem-analysis, model-selection, model-building, assumption-checking]
```

Agent 数量不是 KPI：**~5 个 Role、~14 个 DAG 常驻节点、若干按需 executor**。29 → 目标区间靠"能力归并"达成，不机械合并。

### 1.9 Project 和 Runtime 的关系？

- **Runtime**（`core/runtime|workflows|schemas|validators|evaluation|knowledge|skills|roles`）= 可复用引擎，不含项目数据。
- **Project**（`projects/<p>/`）= 引擎的一次运行实例，含全部状态与产物。
- 引擎与实例严格分离（继承 V2 原则）；V3 新增：**Project 内的 `state/` 目录**承载 status.json / registry.json / evidence_graph.json / decisions.json / workflow.json，与内容产物（`artifacts/`）和临时文件（`scratch/`）物理隔离。

### 1.10 Artifact Lifecycle？

```
draft ──▶ active ──▶ validated ──▶ published
  │          │            │
  └──────────┴────────────┴──▶ invalidated（被上游失效传播命中）
                 │
                 └──▶ superseded（被新版本替代）
任何状态 ──▶ deprecated（人工/流程废弃）
active ──▶ blocked（依赖未满足，可恢复）
```

转换规则（`core/runtime/lifecycle.py` 强制）：

| from | to | 触发 |
|---|---|---|
| draft | active | 产出完成，注册 payload |
| active | validated | 通过对应 validator/critic 门禁 |
| validated | published | 进入 deliverable（论文/支撑材料） |
| active/validated | blocked | 依赖 blocked/invalidated |
| blocked | active | 依赖恢复 |
| 任意 | invalidated | invalidation 传播判定 |
| 任意 | superseded | 新版本 register（同 ID 版本 +1，旧版转 superseded） |
| 任意 | deprecated | 人工或流程废弃 |

非法转换一律拒绝（fail-closed，与 V2 gate 哲学一致）。

### 1.11 Stable ID？

**格式：`<TYPE><NNN>`，项目内唯一、终身稳定、不编码语义、不随文件移动改变。**

| 前缀 | 类型 | 前缀 | 类型 |
|---|---|---|---|
| P | problem | R | result |
| Q | question | F | figure |
| M | model | T | table |
| A | assumption | C | claim |
| DATA | dataset | D | decision |
| CODE | code | N | narrative |
| E | experiment | S | paper_section |
| | | DELIV | deliverable |

- 编号三位零填充，项目内单调递增，由 Registry 分配器发放（`registry.next_id(type)`），**永不复用**。
- 版本独立于 ID：`M002` 永远是 M002，版本体现在 contract 的 `version` 字段（1, 2, 3...），历史版本保留在 Registry（`versions` dict）。
- ID 与路径解耦：contract 存 `payload`（相对项目的路径列表），文件移动只需更新 payload，引用不断链。

### 1.12 Invalidation？

**上游失效时沿 Evidence Graph 向下游传播，分级标记，不粗暴删除。**

传播规则（按 relation 敏感度分级）：

| 上游状态 | 下游经何种边 | 下游判定 |
|---|---|---|
| invalidated | `solved_by / implemented_by / validated_by / uses / assumes / produces / visualized_by / supports / selects / based_on / derived_from` | `invalidated`（直接依赖失效） |
| requires_revalidation | `appears_in / derived_from`（弱依赖，如 claim 出现在章节） | `requires_revalidation`（内容需复查但证据本体未死） |
| dirty | 与 invalidated 节点同 Qi 但无直接边 | `dirty`（建议复查） |
| — | 无路径可达 | `unaffected` |

判定接口：`graph.invalidate(artifact_id)` → 返回 `{"invalidated": [...], "requires_revalidation": [...], "dirty": [...], "unaffected": [...]}` 并写回各 Artifact contract 的 `invalidation` 字段 + 触发 Workflow 引擎把对应 Qi 节点标记需重跑（partial rerun）。

### 1.13 Versioning？

- **Artifact 版本**：contract `version` 整数递增；`update` 产生新版本快照（不可变），`versions[v]` 存历史；引用（relations）默认指向 latest，可显式钉住 `M002@1`。
- **Graph 版本**：`evidence_graph.json` 每次 写入 `graph_version` +1，V2 铁律 W1 的"数值可追溯"升级为"数值可追溯到 Artifact@version"。
- **Schema 版本**：所有 V3 schema 带 `schema_version: 3`，runtime 拒绝未知主版本。

### 1.14 Workflow DAG？

节点类型（7 种）：`reasoning / generation / execution / validation / critique / projection / assembly`。

关键机制：
- **条件边**：`on_pass`（默认）/ `on_fail`（反馈环，指向回退目标节点）
- **反馈环**：`model_critique.on_fail → model_construction`；`evidence_gate.on_fail → experiment_design`；`paper_review.on_fail → paper_sections`
- **并行组**：`experiment_Qi` 兄弟节点、`paper_figures ∥ paper_references`
- **重试**：节点级 `max_retries`（默认 3，继承 V2 Iteration 语义），超限走 on_fail 或 blocked
- **门禁节点**：`validation` 类型节点绑定 validator（gate 断言），fail-closed
- **人工审批点**：`human_approval: true` 的节点进入 `waiting_approval`，由人放行

### 1.15 Per-Qi？

**Question 是一等执行单元（Problem Subtask Entity），不是流水线步骤。**

- 每个 `Q00x` 拥有独立 status / models / experiments / claims / dependencies。
- DAG 中 `experiment` 与 `evidence` 节点带 `per_question: true`，引擎按 problem 分解结果展开为 `experiment_Q001...Q00N` 实例。
- **Q2 失败 → invalidate Q2 子图 → 只重跑 Q2**；Q1/Q3/Q4 若无 `depends_on` 边则完全不触碰。Q3 若 `depends_on: [Q002]` 则标记 `dirty`，待 Q2 重验证后级联评估。

### 1.16 Knowledge Retrieval？

```
输入: {problem_type, features: [数据缺失, 指标相关, 需排序], competition: cumcm}
  ↓ KnowledgeRetriever.recommend()
输出: {
  method_cards:   [排序的候选卡片 + 匹配理由 + 风险 + validation 要求],
  failures:       [历史失败案例（同题型/同方法）],
  patterns:       [可用的创新模式 + required_evidence],
  decisions:      [相关历史决策（含失效原因）]
}
```

评分 = 特征命中（good_for/requires 匹配）+ 竞赛常用度 + 无 failure 红旗加成。**Knowledge 的验收标准是"改变 Agent 的选择"，不是"被读到"。**

### 1.17 Validation Gate？

三层验证体系（继承 V2 门禁哲学并前置）：

1. **Validator（结构性）**：schema 合法 / ID 唯一 / 图无环 / 引用存在——脚本判定，fail-closed
2. **Critic（认知性，前置）**：model-critic / experiment-critic / narrative-critic / judge-critic——在对应 Artifact 产出**当场**审查，fail 触发反馈环
3. **Evidence Gate（准入性）**：没有真实证据不允许进入 paper projection——每个 claim 有 experiment 支撑、每个 experiment 有真实 result、关键实验有 sensitivity + baseline 对比

Judge Critic 输出 `PASS / WEAK / FAIL / UNKNOWN` + Major/Minor Risks + Missing Evidence + Unsupported Claims + Weak Models + Validation Gaps；分数仅作辅助信息。

### 1.18 Legacy Compatibility？

**V2 不删除，包一层适配器，双模式运行至 V3 验证完成。**

- `core/runtime/legacy/convert.py`：
  - `all_results.json` ⇄ `Registry + Evidence Graph`（results→R/F/T artifacts + produces/visualized_by 边）
  - V2 `work/state.json`（29 步）→ V3 `status.json`（映射到多维状态）+ 保留原文件不动
  - V2 产物路径 → Registry artifact（payload 指回原路径，**不搬文件**）
- V2 工具链（state.py / gate.py / orchestrator.py / 29 agent SKILL.md）在 P0-P4 期间保持可用；P5 将 5 scorers + 2 guardrails + revision agents 转为 validators/critics 后，orchestrator 切换到 DAG 引擎，29-step PIPELINE 保留为 `legacy` 模式。
- 判定 V3 "全面验证完成"的标准：真实项目端到端 DAG 运行 + regression 套件全绿——未达标准前 legacy 不下线。

## 2. 目录架构决策（结合审计事实，非机械照搬）

**决策：保留 `core/` 作为引擎容器，V3 层在其内生长；顶层不搞大迁徙。**

理由：catalog.yaml / 30+ 文档 / tests 大量引用 `core/<Hand>/...` 路径；顶层大迁徙=变相 Big Bang，违背分阶段原则。最终结构：

```
core/
├── runtime/                  # ★ V3 运行时
│   ├── artifacts/            #   ids / artifact / lifecycle / registry
│   ├── state/                #   多维状态模型
│   ├── graph/                #   evidence graph + invalidation
│   ├── execution/            #   DAG 引擎 + workflow composer
│   ├── decisions/            #   decision log 运行时
│   ├── knowledge/            #   KnowledgeRetriever 运行时
│   ├── legacy/               #   V2 适配器
│   └── adapters/             #   runtime manifest 生成 / cloud sandbox / harness compat
├── workflows/                # ★ base + competition/ + stages/
├── schemas/                  # ★ 保留 13 个 V2 schema + 新增 v3/ 子树（artifact/...）
├── validators/               # ★ 结构化验证器（从 tools + core/validators/modules 收编）
├── evaluation/               # ★ scoring / benchmark / regression
├── roles/                    # ★ 5 个 Role 组合
├── skills/                   # ★ 重组后的 capability skills（critics 等）
├── knowledge/                #   保留 + 新增 methods/cards, failures/, patterns/
├── agents/                   # ★ V3 DAG 节点 agent 定义（与 legacy 四手并存至 P5）
├── Modeler|Programmer|Writer|Reviewer/   # V2 四手（P5 前保留，P5 降级为 legacy）
├── env/  templates/  tools/  # 保留（tools 逐阶段瘦身）
```

**Project Workspace（新项目标准，V2 项目经 legacy 适配共存）**：

```
projects/<p>/
├── input/            # problem/ + attachments/
├── state/            # ★ registry.json / status.json / evidence_graph.json / decisions.json / workflow.json
├── work/             # per-Qi 工作区 q1..qN（中间推理，非契约）
├── artifacts/        # ★ data/ code/ results/ figures/ tables/（Registry payload 真源）
├── paper/            # source/ figures/ references/ build/
├── deliverables/
├── scratch/          # 临时（原 _scratch，gitignore）
└── logs/
```

`output/` 语义拆解：契约文件 → `state/` + `deliverables/`；中间产物 → `work/` + `artifacts/`。

## 4. 概念边界速查（防"什么都叫 State/Artifact"）

| 问题 | 答案归属 |
|---|---|
| 系统在什么状态？ | State |
| 产出了什么对象？ | Artifact |
| 对象之间什么关系？ | Evidence Graph |
| 下一步做什么？ | Workflow |
| 会不会做错选择？ | Knowledge + Decision Log |
| 做得对不对？ | Validator / Critic / Gate |
| 论文是什么？ | Paper Projection（deliverable Artifact） |
