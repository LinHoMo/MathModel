# A-H 优化必检项

> **重要**：A-H 检查清单面向每个需要维护的**本地脚本/模块**，不能跳过；第三方包依赖只记录，不纳入逐脚本 A-H 覆盖表。

下面 A-H 不是附录，而是默认要逐项筛查的清单。

## 使用方式

1. 先列出入口脚本和所有本地 `include()` / `import` 依赖。
2. 给每个本地脚本（包括入口脚本）建立主表条目。
3. **对每个脚本逐项检查 A-H，不得只挑自己想看的项；标为“重要命中项”的条目必须单独确认。**
4. **A-H 结论必须写入 1.3 主表的"A-H预检结论"列，未填写的脚本不得进入优化。**
5. 若某脚本依赖的辅助脚本命中"共享热路径、顶层执行体、重复初始化、多入口复用"，必须先函数化，再优化该脚本。

主表最小格式：

| 脚本 | 优化状态 | A-H 命中项 | 优化措施 |
| --- | --- | --- | --- |
| `xxx.jl` | `⏳ pending` | `A.顶层执行；D.分配压力` | `-` |
| `yyy.jl` | `N/A` | `N/A：未发现本轮可操作的 A-H 优化点` | `N/A` |

## 正确性验证规则

任何代码修改后，必须执行以下验证：

1. **先建原始基线**：优化前先跑原始代码并记录关键数值；若 `full` 超时或明显超出预算，按 `reduced` / `local` 回退取证；不能用调试脚本或“逻辑相同”代替。
2. **同口径对比**：前后必须使用相同参数、随机种子和验收口径；确定性路径允许合理浮点容差。
3. **验证数值等价**：浮点重排、公共子表达式提取、函数替换、广播融合、并行化都要验，不能只看“数学等价”。
4. **分层验证**：先局部，后整体；`full` 太重时先降级取证，并记录补测计划。
5. **失败即停**：验证失败就停止，并回退或禁用该改动。

常见错误：

- ❌ 修改后直接跑完整仿真，没先验证局部正确性。
- ❌ 前后参数或随机种子不同，结果不可比。
- ❌ 只看总耗时，不看关键中间值。
- ❌ 用调试脚本自测代替入口脚本对比。

## 运行超时处理策略

适用场景：`full` 基准预计超出当前预算、已经超时，或单次执行成本高到会阻断后续分析。

处理原则：

1. 不把 `full` 基准当作每一轮优化的硬前置条件。
2. 优先缩小工作负载获取热点证据，但尽量保持主执行链结构、正确性边界和主要热点形态不变。
3. `reduced` 和 `local` 结果只用于阶段性分析，不替代最终验收。
4. 任何因超时导致的基准降级，都必须在计划文档中记录，并补列后续 `full` 验证事项。

## A. 顶层执行与全局状态

### 命中判断

- **重要命中项：** 存在 TyPlot 绘图。
- **重要命中项：** 热路径还在顶层脚本里运行，而不是在函数内；尤其要检查是否存在循环内直接 `include()`。
- 热路径依赖未常量化或未类型化的全局变量。
- 首次初始化、backend 启动、缓存首填、首次 plan/build 成本被算进稳态 benchmark。
- 循环内重复读取全局配置、字典配置或动态参数。
- 日志、`println`、进度条、调试开关、绘图持续出现在热路径里。

### 优先动作

- 若存在 TyPlot 绘图，入口脚本开始时先调用 `TyPlot.enable_show(false)` 关闭图形显示，避免运行过程中产生不必要的显示开销；脚本结束前再调用 `TyPlot.enable_show(true)` 恢复显示。
- 若存在循环内 `include()`，优先改为函数化或移出循环。
- 把热路径移入函数。
- 把全局状态改成函数参数或 `const`。
- 把一次性初始化移出热路径，必要时先预热再测量。
- 统一线程、RNG、工作目录和缓存预热状态；必要时评估 `BLAS.set_num_threads(1)`。

## B. 类型稳定性

### 命中判断

- 存在 `Any`、不稳定返回值或热点变量类型漂移。
- 容器元素类型、结构体字段类型或热点函数参数过宽、过抽象。
- 热路径混入 `nothing`、`missing`、小 `Union` 或可空返回值。
- 字典查表、配置解析、JSON/文本读取结果直接流入数值热路径。
- 热点路径依赖字符串驱动分派。

### 优先动作

- 引入函数屏障。
- 收紧字段类型、容器元素类型和返回类型。
- 把动态解析、字符串分派移出热路径，改成前置解析或稳定分派。

## C. 闭包与捕获变量

### 命中判断

- 热点路径中存在捕获外部变量的闭包。
- 匿名函数或回调在循环内反复创建。
- 闭包捕获可变容器、外部数组、外部字典或非 `const` 对象。
- 为了省事把热路径包进 `do` 块或局部匿名函数，导致推断困难。

### 优先动作

- 改成具名函数、可调用对象或循环外复用的闭包。
- 避免在热路径中反复构造回调。
- 把闭包依赖的数据改成显式参数。

## D. 分配压力

### 命中判断

- 循环内重复创建临时数组、复制、切片拷贝或字符串对象。
- 同类数组在每轮循环中重复创建，如 `zeros()`、`ones()`、中间切片、副本。
- helper 函数每轮循环做 `a[i, :]`、`a[i:i, :]`、`reshape(a[i, :], ...)`，然后广播或小矩阵乘。
- 循环里用 `x = [x; v]`、`vcat` 逐步拼接，或 `push!` 到未预估容量的数组。
- 本可原地完成的操作，实际走了非原地路径。
- `map`、`filter`、`collect`、`copy`、`vec`、`reshape` 等调用引入了不必要的临时对象。
- `Dict`、`Set`、`Vector` 或缓冲区频繁扩容和 rehash。

### 优先动作

- 评估预分配缓冲区。
- 对逐步增长但长度可预估的数组，先算长度并预分配；对索引列表，优先用 comprehension 或一次性 `collect/filter`，不要在循环里反复拼接。
- 对 helper 中的“行切片 + reshape + 广播/小矩阵乘”，先改成直接循环或 `@views`，再决定是否需要更大算法改写。
- 优先使用 `@view`、`@views`、`mul!`、`randn!`、`append!`、`deleteat!`、`fft!`、`ifft!`、`copyto!` 等原地接口。
- 为容器和缓冲区预估容量。
- 对 KB 级短生命周期小数组，不要默认“预分配一定更快”；先 benchmark 再决定。

## E. 重复计算与融合检查

### 命中判断

- **重要命中项：** 存在公共子表达式、重复查表、重复插值、重复预处理或重复分解。
- 同一数组被多次扫描，而本可合并成一次遍历。
- 同一索引、布尔掩码、排序键、分组键、查表键被重复构造。
- 排序、去重、分桶、分组、窗口切片、合法性检查被重复执行。
- 广播融合后分配下降，但计算次数反而增加。

### 优先动作

- **提取公共子表达式和可复用中间结果。**
- 把重复检查移到进入热路径之前。
- 融合前后同时比较耗时和数值正确性，不只看分配量。

## F. 数值内核、数据布局与内存访问

### 命中判断

- 循环不变量没有提出。
- `permutedims`、转置、维度重排或非连续内存访问拖慢后续 BLAS、FFT 或手写循环。
- 密集矩阵填充或累加的循环顺序不符合 Julia 列主序，例如内层固定第一维、外层才改变第一维，导致缓存访问不连续。
- 小矩阵、小向量、小批次场景误用了通用重型线代/FFT API。
- 热点路径频繁做实复数来回转换、重复类型转换或重复构造数值辅助表。
- 数值循环分支太多，导致 SIMD 难以生效。

### 优先动作

- 提前整理数据布局，让后续访问尽量连续。
- 手写矩阵循环时，优先让第一维索引在最内层变化；如果为了算法顺序必须按行处理，先 benchmark 再决定是否重排数据或改循环。
- 只在 benchmark 明确有收益时，再评估 `sincos`、`cis`、`cispi`、`sinpi`、`cospi`、`Complex(a, b)` 等改写。
- 缓存行为重要时，评估 `Struct of Arrays` 替代 `Array of Structs`。

## G. FFT 与 `Ty*` 库内部热点

### 命中判断

- FFT plan 被重复创建。
- 本可用原地 FFT 或 `rfft/irfft`，实际没有使用。
- FFT 输入来自 `view`、切片或转置重排，触发了隐式复制。
- 同尺寸、同批量、同输入类型的 plan 没有统一复用。
- 绕开了 Syslab / `Ty*` 现有 API，自行重写同类功能。
- 窗口函数、频率轴、索引映射、频域掩码等 FFT 配套对象被重复生成。

### 优先动作

- 统一 plan 尺寸、批量和输入类型，并复用 plan。
- 评估原地 FFT、`rfft/irfft`、可复用缓冲区 + `copyto!`。
- 在替换 `Ty*` API 前，先检查 `syslab-environment` 解析到的帮助文档和现有调用方式。

## H. 并行化

### 命中判断

- **重要命中项：** 多行连续广播彼此独立，适合评估合并为单个 `Threads.@threads for` 循环。
- 当前负载属于独立迭代、批处理、逐样本/逐帧/逐通道/逐块计算、批量 FFT、逐元素或逐窗口处理。
- 单任务耗时足以覆盖线程调度成本。
- 热点确实位于可并行计算段，而不是 I/O、锁竞争、同步或串行初始化。
- 存在可拆分的归约型计算，可以先线程局部累积再合并。
- 当前并行方式存在嵌套并行、负载不均衡、false sharing 或内存带宽争用。

### 优先动作

- 先 benchmark 对比单线程 vs 多线程，再决定是否采用。
- 优先让每个线程处理完整且足够大的工作块。
- 外层并行时，必要时把 BLAS 线程降到 `1`，避免嵌套并行。
- 并行化后同时检查正确性、总耗时、吞吐、额外分配和线程争用。

### 典型模式

```julia
# ❌ 错误：逐行多线程
y1 = similar(x); Threads.@threads for i=1:n; y1[i] = f(x[i]); end
y2 = similar(x); Threads.@threads for i=1:n; y2[i] = g(x[i]); end
y3 = similar(x); Threads.@threads for i=1:n; y3[i] = h(x[i]); end

# ✅ 正确：合并为单个多线程循环
y1 = similar(x); y2 = similar(x); y3 = similar(x)
@inbounds Threads.@threads for i=1:n
    y1[i] = f(x[i])
    y2[i] = g(x[i])
    y3[i] = h(x[i])
end
```
