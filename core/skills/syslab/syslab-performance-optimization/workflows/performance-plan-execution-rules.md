# 计划执行规则

本文件定义默认任务在阶段 1-4 中的唯一合法推进方式。

每个阶段都按同一骨架理解：

- 输入：进入本阶段前必须具备的东西
- 允许动作：本阶段唯一允许推进的工作
- 输出：本阶段必须写回 `docs/performance-plan.md` 或产出的文档
- 进入下一阶段条件：只有满足这些条件，才能继续
- 禁止事项：本阶段不能做的事

## 全局纪律

- `docs/performance-plan.md` 是唯一主控文档
- 一次只允许一个当前执行项处于 `in_progress`
- 任何新增、跳过、重排或扩大范围，都先更新 `docs/performance-plan.md`
- 未写入计划的“顺手优化”不执行
- 所有临时脚本、调试脚本和一次性验证脚本，统一放在对应源文件同级目录的 tmp/ 下
- 所有本地脚本（包括入口脚本）都必须落到明确结论：`done`、`blocked`、`N/A` 或 `dropped`
- `1.3 本地脚本性能跟踪主表` 是唯一逐脚本事实源
- `1.4 逐脚本执行顺序表` 只负责顺序，不重复记录逐脚本事实

## 状态约定

- `pending`：已纳入计划，尚未开始
- `in_progress`：当前正在执行
- `done`：已完成，并有证据
- `blocked`：当前无法继续，有明确阻塞原因
- `revised`：原计划项已重写或重排
- `dropped`：明确移出本轮范围
- `N/A`：经分析确认不适用，并已写明理由

如使用图标，必须和状态词成对出现，不只写图标。

## 任务 ID 约定

为了让计划更容易执行和回填，默认使用以下任务 ID：

- `baseline:<script>`
- `precheck:<script>`
- `functionalize-helper:<script>`
- `optimize:<script>`
- `verify:<script>`
- `overall-review`
- `report:performance`

说明：

- `precheck:<script>` 用于记录该脚本的 A-H 预检查结论
- `functionalize-helper:<script>` 用于记录该脚本所依赖的辅助脚本是否要先函数化
- `optimize:<script>` 和 `verify:<script>` 分别对应优化与验证
- `overall-review` 对应阶段 3
- `report:performance` 对应阶段 4

## 阶段 1. 建立计划

### 输入

- 用户任务
- 项目路径
- 可用的 Syslab 环境
- 已阅读 `workflows/performance-plan-contract.md`
- 已判断这是默认任务，而不是小任务

### 允许动作

- 创建 `docs/performance-plan.md`
- 明确优化目标、正确性约束、精度约束、外部行为约束
- 若入口脚本明确，优先运行 `julia ../scripts/analyze-script-deps.jl <entry1.jl> [entry2.jl ...]`
- 盘点入口脚本、本地依赖脚本、共享模块和公共数据路径
- 建立初始基线、热点证据和验证口径
- 对每个本地脚本完成 A-H 预检查
- 对每个本地脚本写出是否需要先做辅助脚本函数化
- 填写 `1.3 本地脚本性能跟踪主表`
- 填写 `1.4 逐脚本执行顺序表`
- 为每个脚本建立任务 ID 和当前动作

### 输出

- `docs/performance-plan.md` 初版
- 目标定义
- 依赖分析
- 初始基线与热点证据
- 逐脚本主表
- 逐脚本执行顺序

### 进入下一阶段条件

- `docs/performance-plan.md` 已创建
- 所有需要维护的本地脚本都已进入 `1.3` 主表
- 每个脚本都已有 **A-H 逐项检查结论**
- 每个脚本都已有函数化要求结论，或 `N/A`
- 每个脚本都已有当前计划动作
- `1.4` 已能回答"先做谁、依赖谁、做到什么算完成"

### 禁止事项

- 在计划未建好前改代码
- 只在对话里列任务，不写入计划
- **跳过 A-H 逐项检查**
- **A-H 结论未写入主表就进入优化**
- 新建一张平行的逐脚本状态表替代 `1.3`

## 阶段 2. 逐脚本性能优化

### 输入

- 已完成的 `docs/performance-plan.md`
- 已明确的逐脚本顺序
- 已建立的基线、热点证据和验证口径

### 允许动作

对当前脚本严格按以下顺序推进：

1. 执行 `precheck:<script>` 所要求的检查回填
2. 执行 `functionalize-helper:<script>`，或写明 `N/A`
3. 执行 `optimize:<script>`
4. 执行 `verify:<script>`
5. 把结果和证据回填到 `1.3` 主表

额外要求：

- 每次开始一个脚本前，先把当前条目标为 `in_progress`
- 做完立即改为 `done`、`blocked`、`N/A` 或 `dropped`
- 若 `full` 基线超时，可降级到 `reduced` 或 `local`，但必须记录原因和补做计划

### 输出

- 每个脚本的优化结果
- 每个脚本的验证结果
- 每个脚本的证据和状态回填
- 新发现的阻塞项、重排项或 `N/A` 理由

### 进入下一阶段条件

- `1.3` 主表中不再存在待处理的逐脚本 `pending` 项
- 每个本地脚本（包括入口脚本）都已落到 `done`、`blocked`、`N/A` 或 `dropped`
- 每个脚本都已有函数化结论
- 每个脚本都已有优化/验证结论

### 禁止事项

- 辅助脚本函数化要求未完成就直接优化该脚本
- 因为某个热点已经提速，就跳过剩余脚本
- 只写结果摘要，不回填主表
- 跳过验证直接宣布脚本完成

## 阶段 3. 整体性能优化

### 输入

- 阶段 2 已完成
- 所有逐脚本结果已回填主表
- 主表中遗留的 `blocked`、`revised`、`N/A` 项可见

### 允许动作

- 复核局部优化后瓶颈是否转移
- 分析跨脚本共享缓存、重复初始化、重复 I/O、重复 plan 创建、公共缓冲区复用
- 分析局部优化是否改变外部调用方式、输入输出路径或关键副作用顺序
- 评估整体收益主要来自更少计算、更少分配、更稳定类型、更优数据布局还是并行化
- 对 `blocked`、`revised`、`N/A` 项做整体层面的补充说明
- 必要时补做整体 benchmark 或复测

### 输出

- 整体性能优化结论
- 整体复测数据
- 遗留风险与待补验证结论

### 进入下一阶段条件

- 已给出整体收益结论
- 已说明瓶颈是否转移
- 已说明外部行为是否保持不变
- 已说明是否仍有待补的 `full` 验证

### 禁止事项

- 在阶段 2 未完成前进入本阶段
- 用局部热点收益替代整体结论
- 不回扣主表中的 `blocked`、`revised`、`N/A` 项

## 阶段 4. 生成结案报告

### 输入

- 阶段 2 和阶段 3 的结论
- 已更新完成的 `docs/performance-plan.md`

### 允许动作

- 按 `templates/performance-report-template.md` 生成 `docs/performance-report.md`
- 汇总目标、基线、逐脚本结果、整体结果、风险和后续建议
- 回扣 `docs/performance-plan.md` 的主表和阶段结论

### 输出

- `docs/performance-report.md`

### 进入下一阶段条件

- 无；这是结束阶段

### 禁止事项

- 没有正式报告就宣布任务完成
- 报告与计划脱节
- 跳过整体结论，只输出局部 benchmark
