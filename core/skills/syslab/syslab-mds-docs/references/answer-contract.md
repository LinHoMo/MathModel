# 回答与引用约定

## 必需结构

文档类回答至少包含：

1. **直接答案**：先回答用户真正的问题，避免先讲检索过程。
2. **官方依据**：列出实际命中的帮助标题和位置；没有标题时使用可辨识的位置。
3. **可用性说明**：仅当 MDS 未使用或失败时，说明本轮改用了什么来源。

推荐写法：

> Syslab 官方帮助《标题》在“章节或位置”中建议……因此在你的场景里应……

如果工具返回可点击的 `location`，将标题写成链接。若只返回内部路径或标识，按原样简短标注，不虚构 URL、章节或菜单。

## 证据使用

- 将命中片段归纳成结论，不倾倒原始 JSON。
- 优先使用两到三个最相关结果，避免罗列低相关度条目。
- 区分“文档明确说明”“根据文档推断”和“通用建议”。
- 菜单名、选项名或精确限制确有必要时才短引原文；其余内容使用转述。
- 命中结果相互冲突时，优先有明确版本和位置的材料，并说明冲突。

## 降级说明

MDS 不可用时使用一句话即可：

> 本轮未取得 MDS 帮助原文；以下依据来自本机 Syslab 帮助文档（具体路径）。

若所有官方来源都不可用：

> 本轮没有取得 Syslab 官方帮助依据；以下是基于通用经验的建议，具体 API 需再核对。

不要因为无法使用 MDS 而声称后续代码编写、检查或测试一定无法进行。

## 执行交接

用户还要求实际实现时：

1. 把已检索到的产品约束和推荐流程作为实现要求。
2. 根据任务调用 `syslab-environment` 与对应领域技能。
3. 对函数签名再次使用函数文档来源核对。
4. 用对应运行时执行和验证，不把文档命中当作运行成功的证据。
