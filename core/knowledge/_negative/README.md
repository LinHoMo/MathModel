# 负样本库 `_negative`

> 反模式库的落地示例：把 `core/knowledge/pitfalls/antipatterns.md` 里的抽象扣分点，
> 还原成一条条**具体的失败现场**，供 Reviewer 手在评审时对照命中。

## 一、用途

本目录是 Reviewer 手两个 agent 的**落地输入**：

| 消费 agent | 阶段 | 怎么用 `_negative` |
|---|---|---|
| `reviewer/weakness-hunter` | L4（挑缺陷） | 逐条扫描论文时，把负样本当作"命中的长什么样"的标杆：当论文某处写法与本库某个「问题切片」高度相似时，即可按对应 `antipatterns` 编号记为缺陷，并照抄该样本的「失分归因」措辞去写 `evidence` |
| `reviewer/revision-planner` | L5（出修改清单） | 把命中的缺陷转成可执行任务时，直接复用对应样本的「正确做法」与「涉及阶段」，确定回退范围（回 Modeler / Programmer / Writer 的哪一步）与判定式验收标准 |

一句话：**`antipatterns.md` 告诉你"有哪些扣分点"，`_negative/` 告诉你"这个扣分点落到纸面上是什么样、该怎么改"。**

## 二、与 `core/knowledge/pitfalls/antipatterns.md` 的关系

| | `pitfalls/antipatterns.md` | `_negative/`（本目录） |
|---|---|---|
| 性质 | **反模式清单**（抽象规则） | **每条反模式的具体失败现场**（落地案例） |
| 粒度 | 一条一句，只说"扣分点叫什么" | 四段结构，说"现场长什么样、为什么扣、怎么改、在哪一步" |
| 条数 | 30 条通用反模式 | 起步 7 个案例，覆盖 5 类高频反模式 + 2 个补充 |
| 消费方式 | weakness-hunter 逐条扫描的原语 | weakness-hunter 命中判断的参照物 |

**并不重复**：反模式清单管"全"（30 条不遗漏），负样本库管"透"（把最高频、最隐蔽的几条讲穿）。
反模式清单追加新编号后，若属于高频/隐蔽类型，应在本目录补一个对应 `case-*.md`。

## 三、记录格式规范

每个负样本文件统一四段结构，文件名用反模式关键词（`case-NN-<关键词>.md`）：

```markdown
# 负样本：<场景一句话>

> 对应反模式：antipatterns.md #<编号>「<措辞原文>」
> 2 个示例：同一条反模式在单篇论文里反复出现 / 拦都拦不住的"标志性写法"。（如有）

## 问题切片
一段模拟的「论文现场/做法描述」，只写做法与文字，不写具体人名/学校/队号。

## 失分归因
逐条说明为什么扣分，每条都引用 antipatterns.md 的具体编号与措辞，并落到
weakness-hunter 的严重度分级（blocking / major / minor）。

## 正确做法
给出应如何修正，采用「错误 → 修正」对比式写法，直接可转成 revision-planner 的验收标准。

## 涉及阶段
标注命中 Modeler / Programmer / Writer / Reviewer 中哪一手哪个 agent 环节，
并用「产生环节」与「检出环节」区分责任。
```

写作约束：

1. **不出现真实人名 / 学校 / 队号 / 竞赛年份**——负样本是"典型写法"，不是"某篇论文的批斗"。
2. **问题切片要有代入感**——尽量写成一段真会出现在正文里的口吻（包括 LaTeX 片段），
   让 weakness-hunter 扫到类似句子时能一眼对上。
3. **失分归因必须引用编号 + 措辞**——禁止只写"这不好"，要写"命中 antipatterns #N「…」"。
4. **正确做法要可判定**——对到 revision-planner 的验收标准，避免"改进表述"这类空话。

## 五、维护规则

1. `antipatterns.md` 每新增一条高频/隐蔽反模式，本目录补一个对应案例。
2. 每个案例只在**本轮评审切实命中过**后才写——本库是"真实失败现场"，不凭空造案例。
3. 案例文件名与反模式关键词保持一致，便于 `weakness-hunter` 按编号反查。
