# 性能分析与测量规则

本文档同时用于两类场景：

- 建立计划阶段的初始基线、热点探查
- 逐脚本性能优化阶段的脚本级分析与复测

目标是统一完成正确性边界确认、基线建立和热点归因。

## 1. 正确性边界

- 明确用什么检查证明优化后结果仍然有效
- 明确任务所需精度，以及可接受误差范围
- 没有正确性基线时，不进入后续优化

## 2. 基线策略

- 基线必须在 `syslab-environment` 解析出的 Syslab 运行时中建立
- 每次运行都保持工作负载一致
- 先确认正确性与精度基线，再记录性能基线
- 同时记录耗时和分配
- 同时记录线程相关环境：Julia 线程数、BLAS 线程数，以及是否存在其他底层线程池
- 明确测量的是冷态、热态，还是总墙钟时间

### 基准分层

- `full`：真实入口、真实流程、真实口径；只用于可承受时的初始基线和最终验收
- `reduced`：保持主要执行链结构，但缩小输入规模、数据量或迭代次数；分析时通常可以先减少循环次数来保留热点形态并拿到可用数据，避免整轮运行超时
- `local`：只测当前局部热路径；用于解释局部瓶颈

### 超时回退

- 在开始基准前，先写清本轮基准层级和时间预算
- `full` 基准不是每一轮优化的硬阻塞项
- 如果 `full` 超时、预计明显超出当前会话预算，或运行一次就足以中断优化流程，立刻降级到 `reduced` 或 `local`
- 发生超时后，不要反复重跑同一个 `full`
- 先记录超时命令、已运行时长、停止原因和降级后的替代基准
- 降级后仍可继续做热点定位，但必须把“补做 `full` 验证”写成计划条目
- 如果当前任务的主要问题本身就是 `full` 运行超时或不可接受的总耗时，要把这条超时现象直接作为性能证据

## 3. 测量要求

- 优先在函数作用域下测量
- 对外部输入使用插值，避免把全局变量查找成本带入结果
- 如果代码同时包含计算、绘图或 I/O，尽量拆出纯计算内核单独测
- 如果原始工作负载运行时间过长，优先减少循环次数、批次数或迭代规模，先拿到热点分布和主导瓶颈证据
- 把初始化和热循环分开测量
- 大工程不要在每轮迭代里完整预热整个工程；优先只预热当前目标路径、相关模块或代表性工作负载
- 对天然并行的工作负载，不只测单线程基线；尽早补做多线程对照，确认是否存在明确的线程扩展收益
- 如果性能分析或基准代码经过绘图路径，优先考虑 `TyPlot.enable_show(false)`，避免把窗口展示与刷新开销混入默认测量
- `TyPlot.enable_show(false)` 不只是测量隔离手段；对于批量绘图、导图或非交互绘图流程，也要评估是否把它作为正式优化方案的一部分
- 只有当当前目标本身就是绘图展示、渲染或交互行为时，才保留显示开启，并在计划文档和报告里写明原因
- 对 `view`/切片输入的重计算热点（尤其 FFT），要额外记录“是否存在隐式复制”证据；若命中，优先评估可复用缓冲区与可复用 plan

### 至少记录

- 测量命令或 Julia 代码片段
- 输入规模和关键环境参数
- 耗时
- 分配次数或分配字节数
- 基准层级（`full` / `reduced` / `local`）
- 若发生超时：时间预算、已运行时长、回退后的替代层级

## 4. 热点归因顺序

1. 用 `@time`、`@btime` 或 `@benchmark` 做快速测量
2. 用 `@code_warntype` 检查热点函数签名的类型稳定性
3. 只有在热点位置仍不清楚时，才进入 profile

### 4.1 TyFFT 路径补充规则（常见高分配来源）

- 当热点包含 `ty_fft`/`ty_ifft` 且输入来自 `view`、切片或重排结果时，必须检查是否发生隐式 `collect`/复制
- 若命中“每轮重复复制 + 重复 FFT 规划”，优先评估：
  1. 在循环外预分配 FFT 输入缓冲区
  2. 在循环外构建并复用 FFT plan（如 `plan_fft!`）
  3. 循环内使用 `copyto!` + plan 执行
- 评估此类替换时，必须同时给出：局部对照基准（耗时 + 分配）与入口脚本整链路复测结果

### 进入 profile 前

- 如果怀疑采样结果混入旧 workload，先清理旧的 profile 状态，再收集新的样本
- 如果要做分配采样，也先清理旧的分配统计状态，避免不同轮次结果混在一起

## 5. 在建立计划阶段的产物要求

建立计划阶段结束时，必须在 `performance-plan.md` 中至少写出：

- 用户直接执行脚本清单
- 本地脚本性能跟踪主表
- 关键优化项防漏初检结论
- 基线口径与测量方法
- 主导瓶颈列表
- 每个瓶颈的大致占比或影响等级
- 瓶颈之间的依赖关系
- 下一阶段的计划前置条件

> 探查结论必须落到脚本级。不能只写“整体热点在某函数”，而不写它落在哪些脚本行上。

## 6. 在逐脚本性能优化阶段的使用要求

- 每个脚本正式改动前，先补一轮脚本级分析或复测
- 每个脚本完成改动后，至少回填一次前后指标
- 对每个脚本，都要先检查其辅助脚本函数化要求；若有相关辅助脚本，先完成函数化，再做该脚本的局部优化与复测；若无则写 `N/A`
